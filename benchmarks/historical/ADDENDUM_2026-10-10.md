# Addendum 2026-10-10 to the historical selection protocol

`SELECTION_PROTOCOL.md` is unchanged. This addendum was written after candidate intake
closed at 30 and before (a) controlled reproduction of the eight candidates still
marked `candidate`, (b) sealing, and (c) any strategy evaluation of this suite. It
clarifies how existing rules are applied; it does not change inclusion rules, cases,
thresholds, the frozen method, or the evaluation rules.

## A1. Rule 5 via matched runtimes

Each good/bad pair runs in two virtual environments created by `setup_envs.py` with the
same Python (3.11) and the same pinned shared dependencies. The studied distribution
(`pandas` or `scikit-learn`) is the only package allowed to differ. The installed package
sets are recorded in `ENVIRONMENTS.lock.json`, and a pair whose recorded sets differ in
anything else is rejected rather than used. The shared set is the union of both
versions' runtime dependencies at fixed versions: `pytz` stays installed with pandas 3,
and `narwhals`, a dependency that scikit-learn 1.9 added, is also installed with 1.7.2 and
1.8.0, which do not import it. (The pair check found the `narwhals` difference when the
environments were first built, before any of these incidents was reproduced.) Every
environment must also pass `pip check`. Each runner asserts that the installed version of
the studied package equals the component value it was asked to replay.

Every incident in this pilot so far has one changed component. A one-component incident
has two states, and both are endpoints, so it tests verification and status honesty, not
search efficiency. These incidents are reported separately from multi-component search
results and must not be cited as evidence that adaptive search beats other strategies.

## A2. Excluded versus disputed

- `excluded`: failed one or more predeclared eligibility rules at screening, recorded with
  the protocol's reason codes before any reproduction.
- `disputed`: passed screening, but the controlled reproduction, using the predeclared
  test, criterion and threshold, did not show "good passes, bad fails".

A disputed candidate stays in `CANDIDATES.jsonl` with its reproduction outcome. Its case,
criterion and threshold are not modified to make it reproduce. It is not evaluated for
accuracy and is not replaced by another candidate.

A difference between a source's historical claim and the controlled replay is kept in
the candidate's `provenance.json` (claimed versions and behavior next to observed
outcomes). It is not reconciled by editing either side.

## A3. Reporting and one-time evaluation

`evaluate.py` runs once on the sealed suite. It refuses to run if
`benchmarks/results/historical/rows.json` already exists; a later evaluation is a new,
separately documented benchmark version. The run record (`RUN.json`) stores the seal
hash, the frozen source-tree hash, strategies, budgets, seeds, audit and interval.

The report states the full funnel for all 30 logged candidates (excluded by reason code,
sent to reproduction, disputed, included and sealed). It then gives per-strategy
outcomes, with wrong `verified` diagnoses first, followed by correct verified, correct
inferred, unresolved, inconclusive, assumption violations and replay counts. A wrong
`verified` result is reported as a primary finding and is not repaired during this
evaluation.

## A4. Component names

Ledger component names are compared with incident files after PEP 503 normalization,
because distribution names are case-insensitive. The Pillow record lists `Pillow`; its
incident file, replay table and ground truth use `pillow`. The ledger record is unchanged.
